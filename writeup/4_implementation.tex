\FloatBarrier
\section{\texttt{fedctl} System Overview}
\label{sec:impl_overview}

The system consists of two layers. \texttt{fedctl} is the orchestration layer: it packages a Flower application, renders the Nomad\footnote{Nomad is the scheduler and orchestrator used to place runtime services on cluster machines. Appendix~\ref{def:nomad} gives the definition.} jobs that are executed on the Raspberry Pi cluster, and preserves the resulting run evidence. The second layer is the experiment layer, including the tasks, methods, and diagnostics evaluated in Chapter~\ref{chap:evaluation}. This separation keeps execution conditions such as docker images, placement, service discovery, network shaping, and logs separate from task construction, data partitioning, local training, and aggregation.

\hypertarget{implcomp:run}{}\hypertarget{implcomp:dep}{}
\paragraph[Configuration.]{Configuration \impltaghead{implcomp:run}{darkblue}{run}\impltaghead{implcomp:dep}{darkblue}{dep}.\footnote{Throughout the following sections, superscript tags such as \textsuperscript{\textbf{\textcolor{darkblue}{[run]}}} identify the responsible component and link back to its explanatory paragraph.}}
Configuration covers both the experiment workload and the deployment environment. The run config selects the FL method, task, partitioner, model-rate allocation, client sampling, and random seed. The deploy config specifies typed workers placement policy, resource reservations, submit-service settings, and network impairments.

\hypertarget{implcomp:request}{}
\paragraph[CLI and submit service.]{CLI and submit service \impltaghead{implcomp:request}{paletteGreen}{cli}\impltaghead{implcomp:request}{paletteGreen}{svc}.}
The \texttt{fedctl} CLI resolves the project, configs, then prepares the run bundle and submission request. The submit service receives the request, records the experiment, and later orchestrates and schedules the execution.

\hypertarget{implcomp:deploy}{}
\paragraph[Deployment environment.]{Deployment environment \impltaghead{implcomp:deploy}{paletteGreen}{reg}\impltaghead{implcomp:deploy}{paletteGreen}{nomad}\impltaghead{implcomp:deploy}{paletteGreen}{runner}.}
The registry stores the SuperExec image used to launch the Flower application. The Nomad renderer turns the deploy config into concrete nomad jobs to be later deployed, while the submit runner reconstructs the submitted project on the cluster before invoking nomad deployment and flower run. Appendix~\ref{def:containers_registry_submit_runner} defines the registry and submit-runner terminology.

\hypertarget{implcomp:runtime}{}
\paragraph[Flower runtime.]{Flower runtime \impltaghead{implcomp:runtime}{paletteOrange}{roles}\impltaghead{implcomp:runtime}{paletteOrange}{app}.}
The run is executed by Flower roles hosted as Nomad-managed containers: SuperLink, SuperNodes, ServerApp, and ClientApps. These roles provide the communication and execution surface; the research app supplies the method and workload code inside them. Appendix~\ref{def:flower_components} gives detailed definitions of the Flower components.

\hypertarget{implcomp:observability}{}
\paragraph[Observability outputs.]{Observability outputs \impltaghead{implcomp:observability}{gray}{wandb}\impltaghead{implcomp:observability}{gray}{art}\impltaghead{implcomp:observability}{gray}{ui}.}
W\&B captures metrics and summaries; artefacts preserve any generated file of the experiment; submit-service UI provides a web interface for monitoring and managing experiments. See Appendix~\ref{def:network_evidence} for more details.

\hypertarget{implcomp:substrate}{}
\paragraph[Cluster.]{Cluster \impltaghead{implcomp:substrate}{fedstalebrown}{cluster}.}
The cluster provides inventory, Nomad node labels, resource reservations, service networking, and deployment-side network profiles. These properties constrain where and how the FL roles execute.

\FloatBarrier
\section{Run and Deployment Configuration}
\label{sec:impl_configuration}

Configuration is split into two surfaces. The \implterm{darkblue}{run config} \runconf{} describes workload and method choices. The \implterm{darkblue}{deploy config} \deployconf{} describes execution conditions: typed workers, placement, resources, images, and network profile.  This split prevents method parameters from being mixed with deployment conditions, allowing the same workload to be replayed under different hardware and network settings.

See the website \href{http://fedctl.cl.cam.ac.uk/help\#configs}{\underline{configuration help}} (accessible via CL network) for detailed reference.

\FloatBarrier
\subsection[Run config]{Run config \impltaghead{implcomp:run}{darkblue}{run}}

The run config is passed to Flower through its \verb|--run-config| flag. Flower expects a TOML file, while \texttt{fedctl} accepts sectioned TOML grouped by run identity, server budget, client training, and partitioning. Before execution, \texttt{fedctl} validates the sectioned file and writes the normalised flat TOML expected by Flower.

For example, a run-config file can group related hyperparameters:

\begin{codeblock}{toml}
[run]
method = "fedavg"
task = "fashion_mnist"
seed = 1337

[server]
num-server-rounds = 20
min-available-nodes = 4

[client]
local-epochs = 1
learning-rate = 0.01

[partitioner]
type = "dirichlet"
alpha = 0.5
\end{codeblock}

% \paragraph{Lowering to Flower.}
% After validation, \texttt{fedctl} materializes the supported keys as the flat TOML expected by Flower, merges command-line overrides for fields such as seed or learning rate, and passes the resulting file to \texttt{flwr run} through Flower's native \texttt{--run-config} mechanism. The submitted artifact records this effective configuration so the remote request can be reconstructed later.

\FloatBarrier
\subsection[Deploy config]{Deploy config \impltaghead{implcomp:dep}{darkblue}{dep}}

The deploy config is handled by \texttt{fedctl}. \texttt{fedctl} uses it to resolve the submit-service credentials, artefact store, container images, registry, typed SuperNode counts, placement, resource reservations, and network impairment. These settings determine how the run is packaged, uploaded, queued, and rendered into Nomad jobs.

\paragraph{Resolution order.}
Deploy config resolution is ordered so that per-run and per-project choices override user defaults. An explicit \verb|--deploy-config| path has highest priority; otherwise \texttt{fedctl} looks for project-local config, then the global default config, which was created after \texttt{pip install fedctl}.

A minimal deploy config only requires user credentials to communicate with the submit service; other settings have defaults but can be overridden for flexible control. For example:

\hypertarget{example:concrete-deploy-config}{}
\begin{codeblock}{yaml}
submit:
  token: ""        # submit-service bearer token
  user: "alice"    # owner recorded for the submission

deploy:
  supernodes:      # logical SuperNodes by device class
    rpi4: 2        # two logical clients on rpi4 workers
    rpi5: 2        # two logical clients on rpi5 workers
  placement:       # scheduler placement policy
    allow_oversubscribe: true  # allow sharing workers
    spread_across_hosts: true  # prefer different hosts
  resources:       # Nomad resource reservations
    supernode:
      default: { cpu: 1000, mem: 1024 }  # per-SuperNode budget
  network:         # named network-impairment profiles
    default_profile: mild  # fallback for unassigned clients
    profiles:
      none: {}     # no impairment
      mild:        # example impaired profile
        delay_ms: 30   # added latency in milliseconds
        jitter_ms: 5   # delay variation in milliseconds
        loss_pct: 0.5  # packet-loss percentage
\end{codeblock}

The \texttt{submit} block is used before queue submission. It supplies the user, bearer token, submit-service endpoint, artefact store, submit-runner image, and registry defaults; these can be changed for another cluster or registry so enables extensions easily.

The \texttt{deploy} block controls the cluster execution plan. It sets typed SuperNode counts, placement policy, resource reservations, and named \texttt{netem} profiles. \texttt{fedctl} lowers these values into SuperLink, SuperNode, and SuperExec Nomad jobs.

\section{Submission and Cluster Orchestration}
\label{sec:impl_remote_execution}

The \texttt{fedctl submit run} turns a local Flower application into a reproducible cluster run, preserving the submitted configs, deployment state, logs, and result artefacts.

\FloatBarrier
\subsection{Submission lifecycle}

Figure~\ref{fig:remote_execution_lifecycle} summarises the \texttt{fedctl} submission lifecycle.

\begin{figure}[!htbp]
\centering
\makebox[\textwidth][c]{%
  \includegraphics[width=\textwidth]{figures/remote_execution_lifecycle_clean.pdf}%
}
\caption{\textbf{\texttt{fedctl} submission lifecycle.}}
\label{fig:remote_execution_lifecycle}

The lifecycle has four stages. \textbf{(1) Experiment definition:} the request records the Flower application, run config, deploy config, and CLI overrides. \textbf{(2) Submission and admission:} the uploaded bundle archives the project and resolved configs, while the queue stores the request and passes it through typed-capacity and placement checks. \textbf{(3) Nomad and Flower runtime:} the submit runner builds or selects the SuperExec image, renders Nomad jobs, and starts \texttt{flwr run}. \textbf{(4) Evidence surfaces:} metrics, W\&B records, logs, and structured artefacts can be retrieved and used for later evaluation.


\FloatBarrier
\subsection[Submission interface]{Submission interface \impltaghead{implcomp:request}{paletteGreen}{cli}}

The \implterm{paletteGreen}{submit interface} is the user-facing control surface for submitted cluster experiments. \texttt{fedctl submit run} creates the submission; companion commands inspect status, logs, inventory, and results, and can cancel or purge terminal records. See the website \href{http://fedctl.cl.cam.ac.uk/help\#reference}{\underline{reference}} (accessible via CL network) for the full command set documentation page.

To submit a run, the \texttt{fedctl submit run} command takes a Flower project, a run configuration \runconf, and a deployment configuration \deployconf.\footnote{Additional command-line options are supported (e.g., \texttt{--seed}, \texttt{--priority}, and \texttt{--exp}), but only the primary arguments are described here for brevity.}

\begin{codeblock}{bash}
fedctl submit run <flower-project> \
  --run-config <run-config> \
  --deploy-config <deploy-config>
\end{codeblock}

\paragraph{Request capture.}
The \implterm{paletteGreen}{CLI} inspects the Flower project, resolves the configs, applies overrides such as seed or run name, and records the reconstructed user-facing command.

\paragraph{Environment.}
When creating a submission, the CLI uploads the project and resolved configuration material needed by the submit runner. The request can then execute from the submit node independent from the user machine.

The \implterm{paletteGreen}{submit runner} \submitrunner{} builds or reuses the SuperExec image stored in the \implterm{paletteGreen}{registry} \regtag{}. It starts from a Flower SuperExec base image, copies in the submitted project, and installs the project package, so application dependencies are taken from \texttt{pyproject.toml}. The reuse tag hashes the generated Dockerfile, Flower version, and project inputs such as \texttt{pyproject.toml} and \texttt{src/}, allowing identical environments to be reused across runs.

\FloatBarrier
\subsection[Queue admission and dispatch]{Queue admission and dispatch \impltaghead{implcomp:request}{paletteGreen}{svc}\impltaghead{implcomp:substrate}{fedstalebrown}{cluster}}
\label{sec:impl_queued_admission}

The \implterm{paletteGreen}{submit service} passes each submission record into a queue before any Nomad job is scheduled. The record stores the owner, runner arguments, priority, status, job mapping, and logs. The dispatcher fetches the top queue record and checks the live \implterm{fedstalebrown}{Nomad state}; once a request can be admitted, it launches a submit-runner Nomad batch job that downloads the experiment bundle, reports job mappings, then deploys and runs the experiment.

\paragraph{Capacity-aware admission.}
Admission is typed and capacity-aware on top of being first-in-first-out. For strict deployments, the dispatcher admits a run only when the requested device mix is available, so a run asking for ten \texttt{rpi4} and ten \texttt{rpi5} workers waits until the cluster has sufficient capacity. Placement can then spread logical workers across distinct hosts, prefer spreading before reuse, or deliberately oversubscribe physical hosts.\footnote{These choices are controlled through the deploy config under \texttt{deploy.placement}, including \texttt{spread\_across\_hosts}, \texttt{prefer\_spread\_across\_hosts}, and \texttt{allow\_oversubscribe}.} Oversubscribed deployments use live CPU and memory resource constraints rather than exclusive device reservation, and the selected placement policy remains part of the recorded run state.

Figure~\ref{fig:queue_admission_dispatch} provides a concrete example. Running jobs are considered first, then queued pending submissions are checked in order of priority and arrival time. The dispatcher combines the submission record, image, placement policy, live inventory, and existing reservations to decide whether the run can be admitted. If the checks pass, it reserves the client and server capacity before starting the submit runner.

\paragraph{Service discovery.}
Runtime dynamic IP addresses are injected through Nomad service discovery. SuperNodes discover the SuperLink service; the ServerApp receives the SuperLink ServerApp endpoint; and each ClientApp receives the corresponding SuperNode ClientApp endpoint. This makes the deployment robust to changing IPs and ports across runs.

\paragraph{Runtime metadata.}
The renderer also injects experiment and placement metadata into the runtime. ClientApp containers receive the logical client index, device type, experiment identity, and, where strict placement is used, node identity. The research app \researchapp{} records this metadata with client metrics. This allows the evaluation to group training time, update share, and submodel quality by device class.

\section{Controlling Real Hardware Heterogeneity}
\label{sec:impl_heterogeneity_control}

Hardware heterogeneity is inherent in a real edge cluster, but it must be controlled to support reproducible experiments. \texttt{fedctl} exposes two deployment controls: typed client placement for compute heterogeneity, and network impairment for straggler-induced heterogeneity.

\FloatBarrier
\subsection[Typed client placement]{Typed client placement \impltaghead{implcomp:dep}{darkblue}{dep}\impltaghead{implcomp:deploy}{paletteGreen}{nomad}\impltaghead{implcomp:substrate}{fedstalebrown}{cluster}}

Typed client placement turns a requested client topology into scheduler constraints over the physical cluster. A run specifies typed clients, where each type corresponds to a worker class such as \texttt{rpi4} or \texttt{rpi5}. Figure~\ref{fig:device_placement} traces this topology request to the device-labelled metrics used in the evaluation.

\begin{figure}[!htbp]
\centering
\makebox[\textwidth][c]{%
  \includegraphics[width=\textwidth]{figures/device_placement_clean.pdf}%
}
\caption{\textbf{Typed client placement and metadata flow.}}
\label{fig:device_placement}
\end{figure}

\paragraph{Typed clients.}
The interface is the \verb|--supernodes| flag\footnote{In Flower, a SuperNode is the client-side runtime endpoint used in a deployed federation. In \texttt{fedctl}, each typed logical client is materialised as one SuperNode endpoint plus one paired client execution job.}, which defines the logical client topology as typed counts and overrides the deploy config \deployconf{} when present\footnote{If omitted, the same specification is read from \texttt{deploy.supernodes}. In both cases, the run records a typed logical-client topology rather than a flat pool of interchangeable clients.}:
\begin{codeblock}{bash}
fedctl submit run <project>
  --supernodes rpi4=10, rpi5=10
\end{codeblock}


At deployment time, typed clients are mapped onto physical nodes by matching the requested type to \implterm{fedstalebrown}{Nomad node metadata}. Placement can be strictly pinned, constrained by device class, or expressed as soft constraints.\footnote{It is enforced either by pinning to \texttt{node.unique.id} or by constraining \texttt{meta.device\_type}.}

\paragraph{Execution pairing.}
Each typed client is realised as a paired runtime: a Flower SuperNode communication endpoint and a corresponding client execution job. The pair shares a device-class constraint and a common instance index, so each logical client corresponds to exactly one communication endpoint and one execution context.

Device type and identity are exposed to the application via environment variables, and are recorded with client metrics. This links deployment to evaluation: compute-heterogeneity experiments assign different model rates to \texttt{rpi4} and \texttt{rpi5}, while diagnostics such as training time, update share, aggregation weight, and staleness are analysed by device class.

\FloatBarrier
\subsection[Network impairment]{Network impairment \impltaghead{implcomp:dep}{darkblue}{dep}\impltaghead{implcomp:deploy}{paletteGreen}{nomad}}

Network impairment exposes network communication as a deployment variable. The deploy config \deployconf{} assigns a named impairment profile to each logical SuperNode. When a profile is active, \texttt{fedctl} renders the corresponding SuperNode task so that \texttt{flower-supernode} starts through a generated wrapper. The wrapper installs Linux traffic-control rules before executing the SuperNode process. The Flower application therefore observes the same runtime interface; the deployment layer controls the network path.

\texttt{netem} is Linux's network-emulation facility for adding delay, jitter, packet loss, and bandwidth shaping. Figure~\ref{fig:network_impairment} illustrates the network impairment pipeline from profile definition to logical assignment, Nomad rendering, wrapper setup, and ingress/egress enforcement.

\makebox[\textwidth][c]{%

}
\caption{\textbf{Network profile resolution and enforcement.}}

\paragraph{Profiles and assignment.}
A network profile is a named collection of traffic-shaping parameters consumed by the wrapper. \hyperlink{example:concrete-deploy-config}{\underline{earlier deploy-config example}} gives one \texttt{mild} profile. Assignments are resolved after typed placement, so selectors such as \texttt{rpi4[*]} mean all \texttt{rpi4} nodes, while \texttt{rpi5[1]} refers to the first \texttt{rpi5} node. Direction-specific impairment uses the tuple order \texttt{(ingress, egress)}. For example:

\paragraph{Impairment setup.}
At deployment time, \texttt{fedctl} turns the selected profiles into per-SuperNode startup rules. It first validates profile names and expands typed selectors such as \texttt{rpi4[*]} into concrete logical SuperNodes. For each impaired SuperNode, the rendered Nomad task receives the selected profile through \texttt{NET\_*} environment variables and runs a Linux traffic-control wrapper before launching \texttt{flower-supernode}. The wrapper applies egress rules directly on the task interface; for ingress rules, it redirects incoming traffic through an \texttt{ifb} device before applying the same \texttt{netem} and bandwidth controls.

\FloatBarrier
\subsection{FL method implementation}

The method layer implements the families evaluated in Chapter~\ref{chap:evaluation}. Appendix~\ref{appendix:algorithms} gives unified pseudocode for each method; here the emphasis is on the implementation details for deployment.

\paragraph{Full-model synchronous training.}
\texttt{FedAvg} is the full-model synchronous baseline. The server broadcasts the same global model to selected clients, waits for the configured replies, and aggregates returned models by example count.

\paragraph{Submodel training.}
\texttt{HeteroFL}, \texttt{FedRolex}, and \texttt{FIARSE} share one partial-training pipeline: select the client-visible parameter subset, train locally, scatter returned updates back into the global model, and aggregate only covered regions. They differ in the selection rule, as Figure~\ref{fig:model_heterogeneity_method_overview} summarises: fixed nested slices for \texttt{HeteroFL}, rolling windows for \texttt{FedRolex}, and sparse importance masks for \texttt{FIARSE}. \texttt{FIARSE} follows the paper's sparse-mask training mechanism, but executes those masks through dense PyTorch kernels on worker CPUs, so improved submodel quality does not necessarily translate into measured wall-clock speedup.

\paragraph{Buffered asynchronous training.}
\texttt{FedBuff} and \texttt{FedStaleWeight} use a buffered asynchronous server loop so the implementation can control in-flight concurrency, buffering, staleness, and accepted-update logging. \texttt{FedStaleWeight} changes only the buffer weighting rule, using the stale-aware weighting described in Section~\ref{sec:fedstaleweight_related}. The server records both update share and weight share, separating arrival frequency from aggregate influence.

\paragraph{Asynchronous submodel FL.}
\texttt{FedCover} combines the buffered asynchronous loop with HeteroFL-style nested submodels. Each reply carries its model rate and trained parameter slice, allowing the server to scatter the returned delta into the global parameter space and measure which parameters were covered. Section~\ref{sec:fedcover_impl} introduces the resulting coverage-aware aggregation algorithm.

\FloatBarrier
\section{\texttt{FedCover}: Coverage-Aware Buffered Aggregation}
\label{sec:fedcover_impl}

Section~\ref{sec:async_submodel_related} motivates the coverage mismatch created by stale partial submodel replies. This section defines \texttt{FedCover}, the server-side correction used in the implementation. The baseline is \texttt{Async-HeteroFL}: \texttt{FedBuff}-style buffering combined with \texttt{HeteroFL}-style nested slicing. \texttt{FedCover} further rescales each covered parameter delta by a capped inverse-coverage gain.

\paragraph{Buffered submodel replies.}
At server step \(s\), let \(\mathcal{B}_s\) be the accepted buffer, let \(q_i\) be the staleness score for reply \(i\), and let
\[
    \alpha_i =
    \frac{q_i}{\sum_{u\in\mathcal{B}_s}q_u}
\]
be its normalised buffer weight. Let \(I_i\) be the submodel parameter set trained by reply \(i\). The shared asynchronous sign convention is \(\Delta_i=w^{[v_i]}-\tilde{w}_i\), where \(v_i\) is the server version downloaded by the client, with local coordinate \([\Delta_i]_j\) defined when \(j \in I_i\).

\paragraph{Parameter-level coverage.}
The buffered model delta for parameter \(j\) is
\[
    [\bar{\Delta}^{[s]}]_j
    =
    \sum_{i \in \mathcal{B}_s}
    \alpha_i \mathbf{1}[j \in I_i][\Delta_i]_j.
\]
FedCover defines the observed coverage mass \(c_j^{[s]}\) for parameter \(j\) as:,
\[
    c_j^{[s]} =
    \sum_{i \in \mathcal{B}_s}
    \alpha_i \mathbf{1}[j \in I_i].
\]
This can be seen as the sum of the buffer weights for the accepted replies whose submodel contains parameter \(j\). The buffer weights \(\alpha_i\) are normalised over the accepted buffer reply staleness score \(q_i\), so \(0 \le c_j^{[s]} \le 1\). Thus, before correction, parameters covered by stale replies contribute less to the buffered model delta.

\paragraph{Inverse-coverage gain.}
Under nested submodels, shared prefix parameters have high coverage mass, while outer blocks used only by larger model rates have lower coverage mass. 
\texttt{FedCover} scales coverage mass with a capped inverse-coverage gain. Figure~\ref{fig:fedcover_coverage_gain} shows one accepted buffer and the resulting gain curve.

The gain for parameter \(j\) is
\[
    \kappa_j^{[s]}
    =
    \min\!\left(\kappa_{\max}, (c_j^{[s]})^{-\gamma}\right)
    \quad \text{for } c_j^{[s]} > 0.
\]

\paragraph{Corrected server update.}
The server applies
\[
    [w^{[s+1]}]_j
    =
    [w^{[s]}]_j - \eta_s \kappa_j^{[s]}[\bar{\Delta}^{[s]}]_j
    \quad \text{when } c_j^{[s]} > 0,
\]
and leaves \([w^{[s+1]}]_j=[w^{[s]}]_j\) when the buffer contains no update for that parameter. Full coverage gives \(\kappa_j^{[s]}=1\), while lower coverage scales the update by the inverse-coverage gain. The hyperparameter \(\gamma\) controls correction strength, and \(\kappa_{\max}\) prevents excessive amplification.
